# AGENTS.md

Guidance for any coding agent working in this repository.
Read this before making changes. `CLAUDE.md` just points here.

Current backlog, known bugs and their analysis live in `PLAN.md`.

## Project

Educational cross-platform 3D engine. Linux/Vulkan and Windows/DX12. Not production.

macOS/Metal is being brought back — forward pass only, see `PLAN.md` S1.
Metal shaders are MSL compiled at runtime; Xcode is not required.

## Build

After clone: `git submodule update --init`

Get SLANGC from https://github.com/shader-slang/slang/releases → `scripts/tools/slang/`
Windows also needs DXC from https://github.com/microsoft/DirectXShaderCompiler/releases → `scripts/tools/dxc/`

Shader scripts resolve `slangc` in this order: `$SLANGC`, `scripts/tools/slang/bin/slangc`, `PATH`.

Compilers: clang (default) or GCC 13+.

| Platform | Command |
|----------|---------|
| Linux | `./scripts/build_linux.sh` |
| Windows | `scripts\build_win.bat` |
| macOS | `./scripts/build_mac.sh` |

Output: `bin/app` (or `bin/app.exe`), `bin/shaders/`

## Tests

Single test (5-tick headless run):
```bash
./bin/app --script tests/cube_gpu_test.as --ticks 5
```

All tests:
```bash
./scripts/run_tests.sh          # Linux
scripts\run_tests.bat           # Windows
```

Every test runs with `--validation=on --validation-required`, so a run fails if
the graphics API reports an error *or* if the requested validation level is not
available. Override with `VALIDATION=gpu` (adds GPU-assisted and synchronization
validation, slow) or `VALIDATION=off`. The suite also runs `--validation-selftest`
first, which checks the argument parser and the validation sink without a GPU.

On Linux the validation layer comes from the `vulkan-validationlayers` package;
without it every test fails on the requirement, by design.

Logs → `scripts/logs/`

## Architecture

```
engine (main loop)
├── script_manager         AngelScript load + execute
├── window_manager         GLFW windows
├── renderer               frame management, GPU command buffer fill
│   └── dynamic_rhi        abstract RHI interface
│       ├── vk_dynamic_rhi Vulkan (Linux)
│       └── dx_dynamic_rhi DirectX 12 (Windows)
├── scene                  render_objects + camera
└── texture_manager        async load + cache
```

**Modules** (each a static lib linked into main app):
- `lucus-sim` — engine, script integration
- `lucus-core` — base classes, scripting bindings, filesystem
- `lucus-graphics` — RHI, scene, material, mesh, texture
- `lucus-math` — transform, camera (wraps GLM)

## RHI Design

Abstract base `dynamic_rhi` with virtual methods. Factory `create_dynamic_rhi()` returns platform impl.

**Handle pattern** — GPU resources are opaque handles (`mesh_handle`, `texture_handle`, `pipeline_state_handle`, `uniform_buffer_handle`, etc.) generated by `CUSTOM_RESOURCE_HANDLE(T)` macro. Handle stores u32 index (1-indexed; 0 = invalid). RHI impls store actual resources in hash maps keyed by handle index.

**GPU command buffer** — renderer records fixed-size command structs (≤32 bytes) into byte buffer; RHI `execute()` consumes it. Commands: `RENDER_PASS_BEGIN/END`, `BIND_PIPELINE`, `BIND_TEXTURE`, `BIND_VERTEX_BUFFER`, `DRAW_INDEXED`, etc.

## Key Patterns

**Intrusive ref-count**: `object` base class + `intrusive_ptr<T>` smart pointer. Used for mesh, material, texture, camera, scene, render_object.

**Singleton**: template base `singleton<T>` → `window_manager`, `renderer`, `script_manager`, `texture_manager`.

**Factory methods**: `material::create_factory()`, `mesh::create_factory()`, `texture::create_factory()`.

**Script bindings**: `bind_*.cpp` files expose C++ types to AngelScript. Game/test logic lives in `content/scripts/*.as`.

## Code conventions

**Do not leave comments in code.** Write the code so it does not need them:
name things properly, keep functions small, extract a named helper instead of
explaining a block. Delete commented-out code rather than parking it.

Exception — a place where the *reason* cannot be read off the code: a driver
quirk, a spec requirement, a non-obvious ordering constraint, a workaround.
There:

1. **Ask the user first** — say which line, and what the comment would say.
2. Add it only after approval.
3. Keep it as short as possible. One line. State the reason, not the mechanism.

```cpp
// good: minImageCount is a request; the driver may return more
// bad:  resize the vector to hold one image view per swapchain image so that
//       the loop below can push_back without going out of bounds
```

Doc comments on public API follow the same rule: only when the signature cannot
carry the meaning, and only after approval.

This applies to code. `PLAN.md`, `README.md` and commit messages are where
explanation belongs.

## Making changes

- Build and run `./scripts/run_tests.sh` before reporting work as done.
- Tests only check the exit code — a pass does not mean the image is correct.
  Say so when a change affects rendering.
- Do not add workaround build flags; fix the cause.
- Report what was verified and what was not, per platform. Only Linux/Vulkan
  can be run here; DX12 changes are compile-only at best.
